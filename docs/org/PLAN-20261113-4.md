## 一、重建原则（7 条）

1. **单会话单身份**：一个会话只戴一顶帽子；越位即交接换会话。
2. **单一真源**：每类信息只有一份权威（如测试数只认 `tools/test_results.json`）。
3. **文档最小够用**：流程服务功能，不反过来。
4. **活 / 历史 / 生成三分**：`docs/` B 档物理分区。
5. **软重建**：保 git 历史与代码，只重写规范 + 小步搬迁。
6. **可回滚**：每步独立、可 revert。
7. **历史不回改**：旧文不追改，只活文档用新规则。

## 二、人员规划（10 项核对结果）

1. **会话与常驻**：统筹主持 1 个常驻；助理每批新开；工匠每批 1 名（下一期经分析最多 +1）；考官每批必叫（纯文档轻量 ≤5 行）；独立督导按需；组织规划每任务新开；策略顾问按需。
2. **职责 / 写入 / 预算**：见 `docs/TEAM.md` §一。
3. **编制与实例名**：`lead` / `assistant` / `artisan` / `examiner` / `audit-lead` / `auditor` / `audit-cost` / `architect` / `role-planner` / `struct-planner` / `advisor`。
4. **接口协议**：`docs/org/REQUEST.md` 五字段（窗口/关注点/争议/**事实快照**/期望产物）；组织规划先出**提纲**（≤15 行）等用户确认再细化；回执 ≤10 行（结论/方案/影响/风险/待确认/产物）。
5. **命名与身份**：中文职位名沟通；英文实例名只在 spawn 出现；旧名 `builder`/`verifier`/`steward` 禁用。
6. **生命线**：统筹主持 >100 轮 / 压缩 ≥2 / 空回复 1 次告警+压缩、连续 2 次交接；组织规划 ≤20 轮/件；**巡检归独立督导每天**；最终拍板归用户。
7. **权限矩阵**：路径 → 唯一写者；冲突仲裁按 `docs/TEAM.md` §五；主持保留直接修改权但需在 `HANDOFF` 留痕。
8. **成本与度量**：轮次预算表见 `docs/TEAM.md`；8 项指标；docs 提交每批 ≤1 个；token 红线先监控 2 周。
9. **重建口令**：见 `docs/TEAM.md` §二（四会话各一段，可直接复制）。
10. **禁止与失败模式**：见 `docs/TEAM.md` §八。

## 三、流程结构（6 项核对结果）

1. **主流程 12 步**：登记 → 澄清（≤1 轮）→ 合批 → 用户确认 → 派活 → 实现 → 机械门禁+提交 → 考官复核 → 推送前检查 → 发布 → 状态同步 → 回执。
2. **批次**：一批＝一次可构建可验收的最小功能集合，目标 ≤1 天；记录写 `docs/BATCHES.md`（只追加）。
3. **三道门禁**：提交前 / 推送前 / 发布前；任一红整批停。
4. **审查**：触发 6 条；冷却 ≥7 天（用户可书面授权突破）；整改 ≤5 条并入下一功能批，只有 P0 立即处理。
5. **发布与回滚**：发布 = push + tag + CHANGELOG 同批更新；回滚只 `revert`、禁 force push；热修仍过门禁，极端情况先发后补审须留痕。
6. **复盘**：每批 / 每天 / 每次审查 / 每里程碑 / 触发式，分别落到 `BATCHES`、督导报告、`INCIDENTS`/`RETROSPECTIVE`。
