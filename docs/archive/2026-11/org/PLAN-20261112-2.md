## 二、方案对比

### 方案 1：加抬头 + 互指（不改名）— **推荐**

- **改什么**：`docs/TEAM.md` 首行改为「# A 队团队手册（TEAM）」，并加一行「B 队手册见 `docs/audit/TEAM.md`」；
  `docs/audit/TEAM.md` 加对称一行「A 队手册见 `docs/TEAM.md`」。索引沿用 `docs/FILES.md:163,167`（已有）。
- **影响**：0 处引用失效；纯阅读层消歧；不动任何路径。
- **迁移成本**：**极低** —— 2 个文件各 1–2 行；无 git mv、无脚本。
- **谁来做**：A 队手册改动由架构师（随 F1 后 docs 批次）；B 队那行属 B 队文档，由督导执行（架构师不写）。
- **验证**：两文件首行互指；`grep -n "A 队手册\|B 队手册" docs/TEAM.md docs/audit/TEAM.md`。
- **缺点**：路径仍同名；依赖读者看文件头。

### 方案 2：B 队手册改名 + 旧路径跳转 stub（A 队不动）

- **改什么**：`docs/audit/TEAM.md` → `docs/audit/B_TEAM.md`（git mv）；旧 `docs/audit/TEAM.md` 保留 1 行
  「本手册已改名 `B_TEAM.md`，请更新引用」的 stub；14 处 B 路径引用可逐步更新（有 stub 不阻塞）；
  `docs/FILES.md:167` 同步。
- **影响**：B 队文档 owner（督导）执行；A 队 0 改动。
- **迁移成本**：**中** —— 1 次改名 + 1 个 stub + 14 处引用（可分两步：先改名留 stub，后批量改引用），
  且需 B 队 / 督导同意（跨队）。
- **验证**：`ls docs/audit/`；`grep -rn "audit/TEAM.md" docs` 只剩 stub 与待更新引用；FILES 索引正确。
- **优点**：A 队无感；路径层面消除一半歧义（B 队独占 `B_` 前缀）。
- **缺点**：A 队仍叫 `TEAM.md`；若以后 A 队也想改名需再做一次（回到方案 3 的一半）。

### 方案 3：两边对称改名（各留 stub）

- **改什么**：A 队 `docs/TEAM.md` → `docs/TEAM-A.md`；B 队 `docs/audit/TEAM.md` → `docs/audit/TEAM-B.md`；
  两处旧路径留 1 行 stub；A 队 18 处显式引用 + 16 处裸引用、B 队 14 处显式引用、`docs/FILES.md` 两行需更新。
- **影响**：A 队 + B 队文档全域；需两队同时改、验收。
- **迁移成本**：**高** —— ≈32 处显式引用 + 16 处裸引用 + 2 次改名 + 2 个 stub + 索引；
  A 队手册被角色卡 / HANDOVER / HANDOFF / FILES 广泛引用，漏改风险高。
- **验证**：全仓 `grep -rn "TEAM.md"` 只剩 stub 与历史记录；所有链接可打开。
- **优点**：彻底消歧，文件名自带队伍标识。
- **缺点**：成本最高；与「别让流程本身变成负担」冲突，收益仅命名清晰。

## 三、推荐

1. **短期：方案 1**（2 行改动、零迁移，立即消除「开错本」）。
2. 若用户要求**路径层面唯一**（如自动化脚本按文件名匹配），选**方案 2**（只动 B 队一本，成本可控）。
3. **方案 3 不推荐**：收益低、影响面大、需双队同步验收。
