# 督导团队手册（B 队，独立于 A 队）

> 督导团队**不属于** A 队（主持/执行主管/工匠/考官），是平行的一支：
> 自己有主会话、自己管成员、只跟 A 队的主持对接。
> 两边主会话都不干实际审查工作，只做任务流与成员管控。

## 一、编制（3 人）

| 职位 | 默认实例名 | 职责 | 写入范围 |
|---|---|---|---|
| **督导主持** | `audit-lead` | 读 A 队请求、派活、汇总报告、写 `AUDIT_LOG.md` | `docs/audit/`、`docs/AUDIT_LOG.md` |
| **审查员** | `audit-inspector` | 按 `docs/AUDIT.md` 做流程审查，出结论 | `docs/audit/` |
| **成本管理员** | `audit-cost` | 跑 token 统计、看趋势、写成本报告 | `docs/audit/` |

**只读边界**：B 队不写 `native-emu/**`、不改 A 队的 `docs/`（除 `AUDIT_LOG.md`）、不跑构建、不碰凭据。

## 二、与 A 队的接口

| 方向 | 内容 | 载体 |
|---|---|---|
| A → B | 审查请求（窗口/重点/要看的文件/触发条件） | `docs/audit/REQUEST.md`（A 队主持写） |
| B → A | 审查报告（结论/证据/整改/元审查） | `docs/audit/REPORT-<YYYYMMDD>.md` |
| B → A | 成本巡检报告 | `docs/audit/COST-<YYYYMMDD>.md` |
| B → A | 审查台账（谁审的、结论、整改是否闭环） | `docs/AUDIT_LOG.md`（B 队写，A 队只读） |

**A 队只读**：`AUDIT_LOG.md` 由 B 队维护，A 队不得修改，只能在自己的 TODO 里跟进整改。

## 三、运行节奏

1. A 队主持触发条件成立 → 写 `REQUEST.md` → 通知督导主持（用户在会话间转达或粘贴）
2. 督导主持派给审查员；审查员按 `AUDIT.md` 六节输出（40 行上限，超额需申请）
3. 督导主持汇总 → 写 `REPORT-<日期>.md` + 追加 `AUDIT_LOG.md`
4. **两次审查之间**：成本管理员**每天**巡检一次 token，写 `COST-<YYYYMMDD>.md`（用户 2026-11-12 定）
5. 成本异常（单批 +30%、职位占比突增、重复读上升）→ 报督导主持 → 可触发提前审查

## 四、审查请求模板（A 队填）

```markdown
# 审查请求 YYYY-MM-DD
- 触发条件：T2（每 3 个批次）/ T3（事故）/ T6（安全）…
- 审查窗口：<批次名或提交范围>
- 重点看：
  1. …
  2. …
- 已知争议：（A 队自己觉得可能被误判的地方）
- 附件：<报告文件路径>
```

## 五、审查报告模板（B 队填）

```markdown
# 审查报告 YYYY-MM-DD（窗口：…）
## 结论
通过 / 有条件通过 / 不通过
## 证据
| 闸门 | 证据（文件:行号 / 命令） |
## 整改项（≤5 条，带 owner 与期限）
## 元审查
- 触发条件：偏敏感 / 偏宽松 / 合适 + 量化改法
- 督导流程：成本、覆盖、要不要改提示词
- 判定权：有无漏判、豁免是否合规
```

## 六、成本巡检模板（成本管理员填，≤10 行）

```markdown
# 成本巡检 YYYY-MM-DD
- 本周总量：X 亿（input / output / cacheRead 分列）
- 最贵职位：<职位，占比>
- 环比：+X%（是否超 30% 阈值）
- 重复读：<文件×次数>
- 异常：<有/无，具体>
- 建议：<一条>
```

## 七、边界与红线

- B 队**不评价代码风格、不审单个 bug**（那是考官的事）
- B 队**不改 A 队的规范**，只能提「规范补丁建议」
- 审查结论对 A 队有约束力：**不通过 = 暂停发布**，直到整改复查
- 审查频率仍按 `AUDIT.md` 的 T1–T6 + 7 天冷却；**成本巡检是每天，不是每天审查**，别把两者混为一谈

## 八、定时任务的归属

- **成本巡检的定时任务由 B 队主持自己创建**（它才是那个会话的主持），A 队主持不得代建
- 频率：每天（用户 2026-11-12 定）；时间由 B 队主持定，建议日终（如 23:30）
- 每次巡检**开新会话**，不要复用；历史靠 `COST-*.md` 传递
