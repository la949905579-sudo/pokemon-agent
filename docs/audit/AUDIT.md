# 独立督导 / 第三方审查：触发条件与审查标准（AUDIT）

> 目的：用**独立视角**定期检查“我们是怎么干活的”，而不是只检查“做出了什么”。
> 执行者：B 队审查员 `audit-inspector`（一次性会话，提示词见 `docs/roles/b/auditor.md`），由独立督导 `audit-lead` 派活与汇总。
> 原则：**能判定的才写进来**——每条标准都要能回答“通过 / 不通过 / 无数据”。

## 一、什么时候必须启动审查（命中任一条）

| # | 触发条件 | 判据 | 谁来启动 |
|---|---|---|---|
| T1 | 定期 | 每 **14 天**一次 | Lead |
| T2 | 批次累积 | 每完成 **3 个批次** | steward 提醒，Lead 启动 |
| T3 | 事故 | `INCIDENTS.md` 新增且属**影响发布 / 复发 / 凭据**类，24h 内合并为 1 次 | 统筹主持 |
| T4 | 指标恶化 | CI 首过率 < 70% / 打回率 > 30% / 复发率 > 0（由 `tools/metrics.py` 每周一自动判定） | 脚本判定，红即强制启动 |
| T5 | 角色交接 | 统筹主持或助理换人前；**spawn/重建团队也算** | 交接方 |
| T6 | 安全事件 | 任何凭据/签名/权限相关变更（轮换、泄露、新增 secret） | Lead |

**不需要启动审查的情况**：单个 bug 修复、文档措辞调整、单次构建失败（看 CI 日志就够）。
审查不是越勤越好——每次审查都要花一次完整会话，滥用会让流程本身变成负担。

## 一·五、谁运行审查（2026-11-12 修正）

**督导团队（B 队）是独立团队，必须由用户另开会话运行，禁止由 A 队统筹主持 spawn。**

- 统筹主持没有创建会话的能力；`spawn_teammate` 造出来的是**子成员**，上下文由统筹主持创建，
  独立性打折，而且报告会直接进统筹主持的上下文（正好吃掉我们要省的 token）。
- 正确流程：A 队统筹主持写 `docs/audit/REQUEST.md` → 用户开新会话（B 队独立督导 + 审查员 + 成本管理员）
  → 报告写 `docs/audit/REPORT-<日期>.md` → `AUDIT_LOG.md` 由 B 队维护，A 队只读。
  编制与接口见 `docs/audit/TEAM.md`。
- 违规 spawn 的审查：结论**降级采信**，必须在 `AUDIT_LOG.md` 标注。

**冷却期**：两次审查间隔 ≥ **7 天**，除非发生 P0（数据丢失 / 密钥外泄 / 发布事故）。
冷却期内 T4 变红不强制开审，但必须登记，由下次独立督导核定“该豁免是否成立”。

**豁免权**：只有独立督导能批准豁免；统筹主持不得自行豁免，只能挂「待核定」并写理由。

## 二、审查标准（七类，逐条判定）

### A. 流程闸门（对应 HANDOVER/STRUCTURE 的五道门）
| 检查 | 判定方式 |
|---|---|
| 计划→实现：提交是否单一目的 | `git log` 抽样 10 条，看是否有“一次提交干两件事” |
| 实现→验证：是否跑过测试/CI | 每次推送是否有对应构建记录，失败后是否修复再推 |
| 验证→发布：Release 是否对应成功构建 | 逐个 tag 对 commit，看有无旧包/错包 |
| 发布→交接：文档是否同步 | TODO/CHANGELOG 与代码 diff 对账 |
| 事故→固化：复盘是否带“固化” | `INCIDENTS.md` 每条是否都有规范/提示词/检查项改动 |

### B. 文档与代码一致性
- `FILES.md --check` 返回 0
- `NATIVE_EMU_TODO.md` 的 [x] 能在代码里找到、[ ] 确实没做
- `CHANGELOG.md` 最新一节覆盖最近 3 个批次的可感知改动
- `HANDOFF.md` 的 HEAD/CI/Release/测试数与事实一致

### C. 提交卫生
- 无空提交、无 `// build trigger` 类临时注释
- 无调试残留（`*.log`、转储）入库
- 提交信息是“人话”，能直接当 OTA 说明

### D. 验证证据
- 有测试/CI/真机三者中至少两项的证据，且能指到具体位置
- “应该没问题”式结论记为不通过

### E. 交接完整性
- `docs/HANDOVER.md` 的 11 条前置检查（§二）是否逐条有据
- 是否有未推送提交、未结束的后台任务

### F. 凭据纪律
- 仓库与文档里无 token/私钥/口令明文
- `git rev-list --all --objects` 里无 `keystore`
- secret 数量与用途可解释

### G. 角色边界（新）
- Lead 是否在干 steward 的活（读 diff、跑构建、写文档）→ 记为“定位漂移”
- steward 是否越权（改代码、替 Lead 定优先级）→ 记为“越界”
- 是否存在“只有一个人在干活、其他角色空转”的批次

### H. 成本（2026-11-12 起，**只报告**）
> 背景：会话日志已带 `usage`（input/output/cacheRead/total），用户要求独立督导考核 token 消耗。
> 口径：**只报告 + 给改进建议，不设红线**；先跑两轮拿基线，再复议是否设预算。

指标（跑 `node tools/token_report.mjs --since <批次开始日>`，基线见 `docs/generated/METRICS.md`「token 成本」）：

| 指标 | 算法 | 判定 |
|---|---|---|
| 每批次 token 总量 | 窗口内 `input / output / cacheRead / total` 四项求和 | 只报告数字 |
| 各职位占比 | 按会话 `subagent/descriptor.label` 归类，给 total 与 output 两个口径 | 只报告；无标签会话按会话单列，不猜 |
| 汇报超限次数 | 汇报行数 > TEAM 三·七 上限的次数 | 人工统计；没数据写「无数据」 |
| 重复读同一文件 | 同一会话内 `read` 同一 `file_path` 的次数（额外读 = n-1 求和） | 只报告；给 top 文件 |

**不设红线**：单点数字不触发审查；只有「占用异常大 + 有可执行改法」才写进整改项（每轮最多 1 条）。
两轮（两个里程碑）后由统筹主持复议是否设预算，复议前保持只报告。

## 三、输出与整改闭环

固定输出**六节、默认 ≤40 行（口径对齐 `docs/audit/TEAM.md` §五）**（确实需要更多时，首行写「申请 +N 行：原因」，统筹主持批，单次最多 +20）：

1. **结论**：通过 / 有条件通过 / 不通过 —— 一句话理由
2. **证据**：行号 / 命令输出 / run 链接，并标明对应第二节哪一类（A–H）
3. **整改项**：最多 5 条，每条带 owner 与期限；“风险预警”压进这里作为预防项
4. **下次复查点与元审查**：3–5 条可核验的复查项 + 第五节的三组问题（**不单独加节**）
5. **成本**（H 类，≤5 行）：最贵职位 / 最贵批次 / 一条改进建议（只报告，不设红线）

整改规则：
- “不通过” → **暂停发布**，只允许修整改项，复查通过才恢复
- 整改项超过 **5 条** → 说明流程已经崩了，先做减法（删规范、并角色），不要继续加规则
- 每条整改必须落到三处之一：规范（docs/）、提示词（docs/roles/）、检查项（脚本/清单），否则下次审查不予采信

## 四、审查的边界（防止审查变成负担）

- 审查员 `audit-inspector` **只读**：不改代码、不改文档、不跑构建发布
- 单次审查默认 **40 行**；确实需要更多时，首行写「申请 +N 行：原因」，统筹主持批（单次最多 +20）
- 不重复审上一轮已经通过且无变化的项
- 不评价代码风格、单点性能——那是 examiner 的事

## 五、元审查（独立督导审自己，每次必做）

每次审查必须额外回答三组问题，否则审查不算完成：

### 5.1 触发条件是否合理
- 最近一个周期里，触发了哪些条件、实际启动了几次？
- **T4 已脚本化**：核对 `docs/generated/METRICS.md` 的生成时间是否覆盖本窗口；脚本没跑记为“无数据”，
  不能算“指标正常”。
- **过敏感**的表现：同一原因反复触发、单日触发 ≥3 条、审查间隔 < 7 天
- **过宽松**的表现：该审的窗口没触发（漏判）、事故后没启动、指标恶化无人发现
- 结论必须给**量化改法**，例如：「T3 收窄为仅‘返工>2 次或影响发布’」「加入 7 天冷却期」
  「T4 阈值从 70% 提到 80%」——不接受“建议优化”这种空话

### 5.2 督导流程本身
- 覆盖面：七类标准里哪几类没有数据、为什么
- 成本：这次审查用了多少轮、是否超出“60 行结论”的预算
- 有效性：上轮整改项是否真的落地（抽查 2 条）
- 是否需要改审查员提示词（`docs/roles/b/auditor.md`；文件名沿用，职位名=`audit-inspector`）

### 5.3 判定权的漏洞
- 有没有“该审没审”的窗口？是谁判的、理由是否成立？
- 豁免是否留痕？连续两次漏判是否触发 INC？

## 六、元审查的输出要求

元审查**不单独加节**，写在固定输出的**第六节**（见 `docs/audit/TEAM.md` §五 六节模板）：

```
### 元审查
- 触发条件：偏敏感 / 偏宽松 / 合适（给数据 + 给改法）
- 督导流程：本次成本 <轮次>，覆盖 <n>/7 类；建议改 <具体条目>
- 判定权：<有无漏判、豁免是否合规>
```
