# 复盘 2026-11-14：C4 治理批成本超阈（1.9%）

> 归属：A 队 ｜ 生命周期：活（跟踪至 R1–R5 验收） ｜ 维护者：代理人（proxy）
> 触发：`docs/TEAM.md` §三·十 成本双判据——C4 `perBatch` 20,374,112 > 阈值 19,992,683（超 **1.9%**；≤30M/批 达标）→「记超须复盘」（§七 #10）。
> 说明：只复盘、不改旧文；`RETROSPECTIVE.md` / `RETROSPECTIVE-20261113.md` 正文不回改。

## 一、现象（实测，数字出处：`.pilot/C4/cost-before.json` + `cost.json` + `result.md`）

- **基线**（A open 时落）：windowTotal 117,604,016 ÷ 5 批 = 23,520,803/批；阈值（×0.85）= 19,992,683。
- **C4 增量**（accepted 后取）：windowTotal 137,978,128 − 117,604,016 = **20,374,112**；batches=1 → perBatch = **20,374,112**。
- **判据**：20,374,112 > 19,992,683（超 1.9%）；20.4M ≤ 30M/批 ✓ → 双判据未全过，METRICS #10 记超。
- **对照**：已 accepted 合同均值 15.0M/批（#10），C4 高约 36%；但 C4 仍低于当日 5 批均值 23.52M。

## 二、根因（按贡献排序）

1. **阈值口径是「持续降本」而非「异常线」**（机制性）：阈值 = 0.85 × 当日窗口均值，任何高于均值 85% 的批都记超。C4 20.4M 低于均值 23.5M，却高于 19.99M——这是口径设计的必然，不是异常。
2. **C4 内容本身更重**（主要）：治理批 v1.4 = 新工具×3（`cost_snapshot --before` / `contract_check` 阻断 / `contract_close` 新建）+ 3 个测试文件 + 真机执行首次实战 + 台账全量重生成（FILES/METRICS/BATCHES/HANDOFF），16 文件 +838/−63。工具改动写完后还要读测试回执、复算数字，是 token 大户。
3. **首次真机 FAIL 重试**（显性浪费）：realdevice 首跑 `emu_probe` 因 NativeEmu 未前台 FAIL，拉起后复跑 PASS——多 1 轮启动 + 排查（未单独计量）。
4. **可归因粒度不足**（观察项，不判红）：`byRole` 是当日窗口全量（主会话 63.2M/45.8%、助理 39.0M/28.3%、未标注 26.6M/19.3%、考官 9.2M/6.7%），无法把 20.4M 精确拆到角色；「未标注职位」占 19.3% 说明 spawn 时职位标注不全。

## 三、对策

1. **不调阈值**：双判据（≤基线×0.85 且 ≤30M）不变；「记超 + 复盘」常态处理，不为单批记超回退口径。
2. **真机首跑预检**（写入 C5 合同 §9）：真机执行开工前先确认 NativeEmu 前台再跑 `emu_probe`；回执必写「首跑 PASS/FAIL + 重试次数」。
3. **spawn 显式标职位**（写入 C5 合同 §6/§9）：减少「未标注职位」，C5 起 `cost.json` 的 `byRole` 可按角色归因。
4. **治理批减重**：新工具 ≤2 个/治理批；每工具测试 ≥3 例即可；台账重生成由助理一次性做，A/B 不重复跑。
5. **基线留证**：C5 起 `cost-before` 由 `cost_snapshot --before` 自动落（C4 手动快照为最后一次），杜绝人工口径差。
