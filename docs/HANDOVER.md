# 交接标准（HANDOVER）

> 交接不是"说一声我走了"：有触发条件、前置检查、验收动作。
> 核心原则：**远端仓库 + `HANDOFF.md` 是唯一真源，聊天记录不算**。
> 2026-11-13 重建版：判断权、阈值、助理轮换均按新编制更新。

## 零、谁判断、多久查、查到怎么办

**三层判断（缺一层都不算闭环）**

| 层 | 谁 | 做什么 |
|---|---|---|
| 硬指标（自动交接，不商量） | **各会话自检** | 每次任务结束跑 `node tools/session_health.mjs`；exit 1 即该会话必须交接 |
| 外部巡检 | **独立督导**（每天一次，并入成本巡检） | `node tools/token_report.mjs --json` 看全体会话轮次；超线的在报告里标「应交接」+ 会话 id + 数字 |
| 最终拍板 | **用户** | 可随时强制换会话，也可决定「这次先不换」 |

**说明**：会话越接近阈值越容易自检失灵，所以必须有外部巡检；但督导只判、不替人换；统筹主持不给自己判交接。

## 一、什么时候必须交接（阈值，按职位）

| 职位 | 触发条件（命中任一） | 动作 |
|---|---|---|
| **统筹主持** | 轮次 > 100 | 交接 |
| | 上下文压缩 ≥ 2 次 | 交接 |
| | 出现空回复（只有 reasoning 没正文） | 1 次：告警 + 压缩后继续；连续 2 次：交接 |
| | 同一问题被打回 3 次 | 交接，换视角 |
| | 一个阶段完成、下一阶段性质不同 | 主动交接 |
| **助理** | 每批新开；空回复 1 次 | 直接换新助理 |
| | 批次结束 / 已发布 | 关闭 |
| **工匠** | 单任务完成且考官通过 | 交回助理 |
| | 同一处被打回 2 次 | 停止，交回 |
| | 任务跨 3 个以上模块 | 拆任务，交回 |
| **考官** | 结论已出 | 结束（天然短任务） |
| | 单次复核 > 30 分钟，或问题 > 8 条 | 拆批 |
| **独立督导** | 报告已出 | 结束（一次性会话） |
| **组织规划** | 单件任务 > 20 轮；或压缩 ≥ 2；或连续 2 轮空回复 | 交接或关闭 |
| | 任务完成 | 关闭（不常驻） |
| **分工 / 结构规划员** | 单件 > 10 轮；或完成 | 关闭 |
| **策略顾问** | 单次 > 10 轮；或完成 | 关闭 |

> 用户可推翻任何一条：可以要求提前交接，也可以要求「这次不换」。

## 二、交接前置检查（缺一条都不算完成）

1. `git status` 干净，没有未提交改动
2. 所有提交**已推送到远端**（远端是真源）
3. CI 绿；若有红，必须在 `HANDOFF` 写清原因与下一步
4. `python3 run_tests.py` 通过（数量/结果以 `tools/test_results.json` 为准，不写死）
5. `docs/NATIVE_EMU_TODO.md` / `docs/history/CHANGELOG.md` 与代码同步
6. `python3 tools/gen_files_index.py` 重生成，`--check` 返回 0
7. `docs/HANDOFF.md` 更新：当前状态、阻塞、下一步、**不要做什么**
8. 没有未结束的后台任务（job）或未完成的子代理（合同制 watcher 属运行时、不算未结束 job；交接前须 kill，并在 `HANDOFF` 写「watcher 已 kill / 接管命令」）
9. `tools/precommit_check.sh --push` 通过（远端未被 amend 改写、待推提交非空、提交信息非空）
10. 若有 Kotlin UI 改动：`python3 tools/check_ui_state.py` 无「只写不读」状态（INC-006）
11. 机械闸门已装：`ls .git/hooks/pre-commit .git/hooks/pre-push` 两个都在

## 三、交接内容模板

```markdown
## 交接（YYYY-MM-DD HH:MM）
- 当前目标：
- 已完成：（带 commit hash）
- 未完成 / 卡住：（原因 + 需要什么才能继续）
- 审查状态/豁免凭据：（最近审查结论 / 豁免记录 / 冷却状态；无则写「无」）
- 关键决策：（为什么这么做，以及为什么不那么做）
- 下一步建议：（第一条命令 / 第一个文件）
- 不要做什么：（已知的坑，避免下一位重复踩）
```

最后一条最容易被省，但最值钱。比如「别用空提交触发构建」「keystore 先别动，轮换会导致已装 App 无法覆盖升级」。

## 三·五、助理轮换（每批新开）

助理干重活，**每批新开一个**，批次结束即关闭——目的是让统筹主持始终只读压缩回执，不被长文拖胖。

**交接内容**（写进 `HANDOFF.md` 的「当前批次」小节）：
```
- 批次：<名称>｜进度：<做到哪一步>
- 未完成：<文件/任务>｜卡在：<原因>
- 未推送提交：<有/无，几个>
- 下一步：<第一条命令或第一个文件>
- 不要做什么：<本轮踩过的坑>
```

**交接前必须**：推送所有提交、工作区干净、CI 结论已知、测试结果已知。

**接手 5 分钟**：`git status` 空 → HEAD 与 HANDOFF 一致 → `origin/master..HEAD` 为 0 → `run_tests.py` 全绿（见 `tools/test_results.json`）→ Kotlin 单测通过。

## 三·六、统筹主持与助理的分界（防漂移）

| 动作 | 统筹主持 | 助理 |
|---|---|---|
| 读 `git diff` / 构建日志 / 文件全文 | ❌（除非用户要求） | ✅ |
| 跑命令、push、等 CI | ❌ | ✅（推送需许可） |
| 写 `docs/` 状态类文档 | ❌（保留直接修改权，改后留痕） | ✅ |
| 定优先级、排批次 | ✅ | ❌ |
| 对用户说话 | ✅ | ❌ |
| 跨会话协调 | ✅ | ❌ |
| 最终发布决定 | ✅ | ❌ |

**主持越界（自己去看 diff / 跑构建）= 定位漂移**，记一条失败样本；连续两次说明助理没承担起来。

## 四、反模式（出现即打回）

- 只在聊天里交接，没写进 `HANDOFF.md`
- 带着未提交改动或红的 CI 交接
- 交接前"顺手再改一点"，结果改到一半
- 用"应该没问题"代替证据
- 只写状态不写理由
- **双身份兼岗**（同一会话既当主持又当其他职位）
- **口头派活**（没落 `REQUEST.md` / 任务卡）
- **组织规划直接提交推送**（越权；应转助理）

## 五、接手方验收（5 分钟）

```bash
cd /root/workspace
git status --short          # 期望：空
git log -1 --pretty='%h %s' # 期望：与 HANDOFF 记录的 HEAD 一致
git rev-list --count origin/master..HEAD   # 期望：0
python3 run_tests.py        # 期望：全部通过（最近结果见 tools/test_results.json）
python3 tools/gen_files_index.py --check   # 期望：0
```

任何一条对不上，说明交接不完整——先补齐再干活。
