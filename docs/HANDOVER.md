# 交接标准（HANDOVER）

> 交接不是"说一声我走了"，是有触发条件、有前置检查、有验收动作的流程。
> 核心原则：**远端仓库 + HANDOFF 是唯一真源，聊天记录不算**。

## 一、什么时候必须交接（阈值）

| 角色 | 触发条件（命中任一条） | 动作 |
|---|---|---|
| `lead` | 会话 > 100 轮 | 主动交接 |
| `lead` | 上下文被压缩 ≥ 2 次 | 主动交接 |
| `lead` | 出现 1 次空回复（只有 reasoning、没有正文） | 立即交接 |
| `lead` | 同一问题被打回 3 次 | 交接，换视角 |
| `lead` | 一个阶段完成、下一阶段性质不同（如从修 bug 转到重构） | 主动交接 |
| `builder` | 单个任务完成且考官通过 | 交回 Lead |
| `builder` | 同一处被打回 2 次 | 停止，交回 |
| `builder` | 任务要跨 3 个以上模块 | 拆任务，交回 |
| `verifier` | 结论已出 | 结束（天然短任务） |
| `verifier` | 单次复核 > 30 分钟，或问题 > 8 条 | 拆批 |
| `auditor` | 报告已出 | 结束（一次性会话） |

**不要等到"实在不行了"才交接。** 空回复出现一次就说明上下文已经在退化，第二次只是时间问题。

## 二、交接前置检查（缺一条都不算完成）

1. `git status` 干净，没有未提交改动
2. 所有提交**已推送到远端**（远端是真源）
3. CI 绿；如果有红，必须在 HANDOFF 里写清原因和下一步
4. `python3 run_tests.py` 通过（当前 28/28）
5. `docs/NATIVE_EMU_TODO.md` / `CHANGELOG.md` 与代码同步
6. `python3 tools/gen_files_index.py` 重新生成，`--check` 返回 0
7. `docs/HANDOFF.md` 更新：当前状态、阻塞、下一步、**不要做什么**
8. 没有未结束的后台任务（job）或未完成的子代理

## 三、交接内容模板

```markdown
## 交接（YYYY-MM-DD HH:MM）
- 当前目标：
- 已完成：（带 commit hash）
- 未完成 / 卡住：（原因 + 需要什么才能继续）
- 关键决策：（为什么这么做，以及为什么不那么做）
- 下一步建议：（第一条命令 / 第一个文件）
- 不要做什么：（已知的坑，避免下一位重复踩）
```

最后一条最容易被省，但最值钱。比如"别用空提交触发构建""keystore 先别动，轮换会导致已装 App 无法覆盖升级"。

## 四、反模式（出现即打回）

- 只在聊天里交接，没写进 `HANDOFF.md`
- 带着未提交改动或红的 CI 交接
- 交接前"顺手再改一点"，结果改到一半
- 用"应该没问题"代替证据
- 只写状态不写理由（下一位不知道为什么，就会重蹈覆辙）

## 五、接手方验收（5 分钟）

新会话开工第一步，跑这四条并核对期望值：

```bash
cd /root/workspace
git status --short          # 期望：空
git log -1 --pretty='%h %s' # 期望：与 HANDOFF 记录的 HEAD 一致
git rev-list --count origin/master..HEAD   # 期望：0（没有未推送提交）
python3 run_tests.py        # 期望：28/28 通过
```

任何一条对不上，说明交接不完整——先补齐再干活。
