# 交接标准（HANDOVER）

> 交接不是"说一声我走了"，是有触发条件、有前置检查、有验收动作的流程。
> 核心原则：**远端仓库 + HANDOFF 是唯一真源，聊天记录不算**。

## 零、谁来查、多久查一次、查到了怎么办

**谁来查**：Lead 自己，用脚本，不靠感觉：

```bash
node tools/session_health.mjs        # 轮次 / 压缩次数 / 连续空回合；exit 1 = 该交接
```

**多久查一次**（三条线）：

| 时机 | 动作 | 性质 |
|---|---|---|
| 每个批次结束时（push 之前） | 跑一次脚本，把结果写进交付说明 | 例行 |
| 每次交接之前 | 必跑，作为客观依据 | 例行 |
| 每周 | 用 `docs/roles/auditor.md` 开新会话做流程审查 | 独立审查，不交接 |

**触发后会不会自动交接**：

- **硬触发 = 自动交接，不商量**：脚本 exit 1（轮次 >100 / 压缩 ≥2 / 连续 2 轮空回复）、
  或 CI 连续失败 2 次、或同一问题被打回 2 次。继续下去的产出已经不可靠，换人比硬撑便宜。
- **软触发 = 判断后交接**：任务批次完成、阶段性质变化。由 Lead 决定，**必须写理由**，
  用户可否决。
- **定期审查不触发交接**：auditor 只出报告，换不换人仍按上面两条判定。

**交接动作**：按 §二 前置检查 → §三 模板写进 `HANDOFF.md` → 新会话按 `TEAM.md` §二 重建团队。

## 一、什么时候必须交接（阈值）

| 角色 | 触发条件（命中任一条） | 动作 |
|---|---|---|
| 主持 | 会话 > 100 轮 | 主动交接 |
| 主持 | 上下文被压缩 ≥ 2 次 | 主动交接 |
| 主持 | 出现 1 次空回复（只有 reasoning、没有正文） | 立即交接 |
| 主持 | 同一问题被打回 3 次 | 交接，换视角 |
| 主持 | 一个阶段完成、下一阶段性质不同（如从修 bug 转到重构） | 主动交接 |
| 工匠 | 单个任务完成且考官通过 | 交回 Lead |
| 工匠 | 同一处被打回 2 次 | 停止，交回 |
| 工匠 | 任务要跨 3 个以上模块 | 拆任务，交回 |
| 考官 | 结论已出 | 结束（天然短任务） |
| 考官 | 单次复核 > 30 分钟，或问题 > 8 条 | 拆批 |
| 督导 | 报告已出 | 结束（一次性会话） |

**不要等到"实在不行了"才交接。** 空回复出现一次就说明上下文已经在退化，第二次只是时间问题。

## 二、交接前置检查（缺一条都不算完成）

1. `git status` 干净，没有未提交改动
2. 所有提交**已推送到远端**（远端是真源）
3. CI 绿；如果有红，必须在 HANDOFF 里写清原因和下一步
4. `python3 run_tests.py` 通过（当前 28/28）
5. `docs/NATIVE_EMU_TODO.md` / `CHANGELOG.md` 与代码同步
6. `python3 tools/gen_files_index.py` 重新生成，`--check` 返回 0
7. `docs/HANDOFF.md` 更新：当前状态、阻塞、下一步、**不要做什么**
8. 没有未结束的后台任务（job）或未完成的子代理

## 三、交接内容模板

```markdown
## 交接（YYYY-MM-DD HH:MM）
- 当前目标：
- 已完成：（带 commit hash）
- 未完成 / 卡住：（原因 + 需要什么才能继续）
- 关键决策：（为什么这么做，以及为什么不那么做）
- 下一步建议：（第一条命令 / 第一个文件）
- 不要做什么：（已知的坑，避免下一位重复踩）
```

最后一条最容易被省，但最值钱。比如"别用空提交触发构建""keystore 先别动，轮换会导致已装 App 无法覆盖升级"。

## 三·五、执行主管轮换（2026-11-12 起）

执行主管干重活，**它才是该被轮换的角色**，主持尽量不动。

**触发**：每 3 个批次、或上下文压缩 ≥1 次、或出现空回复 1 次。

**交接内容**（写进 `HANDOFF.md` 的「当前批次」小节）：
```
- 批次：<名称>｜进度：<做到哪一步>
- 未完成：<文件/任务>｜卡在：<原因>
- 未推送提交：<有/无，几个>
- 下一步：<第一条命令或第一个文件>
- 不要做什么：<本轮踩过的坑>
```

**交接前必须**：推送所有提交、工作区干净、CI 结论已知、测试结果已知。

**接手方 5 分钟**：`git status` 空 → HEAD 与 HANDOFF 一致 → `origin/master..HEAD` 为 0 →
`run_tests.py` 28/28 → Kotlin 单测通过。

## 三·六、主持与执行主管的分界（防漂移）

| 动作 | 主持 | 执行主管 |
|---|---|---|
| 读 `git diff` / 构建日志 / 文件全文 | ❌ | ✅ |
| 跑命令、push、等 CI | ❌ | ✅ |
| 写 `docs/` | ❌ | ✅ |
| 定优先级、排批次 | ✅ | ❌ |
| 对用户说话 | ✅ | ❌ |
| 跨会话协调 | ✅ | ❌ |
| 最终发布决定 | ✅ | ❌ |

**主持越界（自己去看 diff/跑构建）= 定位漂移**，督导会记一条；连续两次说明执行主管没有承担起来。

## 四、反模式（出现即打回）

- 只在聊天里交接，没写进 `HANDOFF.md`
- 带着未提交改动或红的 CI 交接
- 交接前"顺手再改一点"，结果改到一半
- 用"应该没问题"代替证据
- 只写状态不写理由（下一位不知道为什么，就会重蹈覆辙）

## 五、接手方验收（5 分钟）

新会话开工第一步，跑这四条并核对期望值：

```bash
cd /root/workspace
git status --short          # 期望：空
git log -1 --pretty='%h %s' # 期望：与 HANDOFF 记录的 HEAD 一致
git rev-list --count origin/master..HEAD   # 期望：0（没有未推送提交）
python3 run_tests.py        # 期望：28/28 通过
```

任何一条对不上，说明交接不完整——先补齐再干活。
